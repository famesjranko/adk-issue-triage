Triage Agent Anatomy

An agent that reads a GitHub issue and predicts the labels a human already applied to it — so every claim it makes can be scored against ground truth nobody invented for the demo. This page explains what each layer does, what to run to watch it happen, and what is still unfinished.

deterministic code probabilistic model halts the run

The idea in one line

Put the model where judgement is needed. Put code everywhere else.

Six steps run for every triage: fetch the issue, then analyse three things that don’t depend on each other, then assign a priority, then judge readiness. That order never changes and never depends on the issue. So it is encoded as a graph — not described in a prompt and rediscovered by the model on every single request.

Only the judgements are model calls. The same reasoning decides where authorisation lives: the model may propose a write to GitHub, but code decides whether it happens.

Runnerruntime

Executes the agent tree. Owns the session, the event stream, and the plugins. This is the piece that adk web hides from you, which is exactly why there is a script that wires it by hand.

scripts/triage.py

Pluginscross-cutting

Registered once on the Runner, so they see every agent. Two of them: a rate limiter keeping one sliding window per model (the free tier’s quota is per model, and the fan-out fires three calls at once), and a token meter, because six model steps per triage is a cost nothing else in the code makes visible.

issue_triage/plugins.py

Graphcontrol flow

The fixed topology: intake → fan out to three analysts → join → priority → readiness → emit JSON. Edges, not prompts. Two versions exist side by side so they can be compared — the deprecated SequentialAgent/ParallelAgent form and the graph Workflow that replaces it.

issue_triage/agent.py · issue_triage/workflow_agent.py

Agentsjudgement

Seven small single-purpose model calls, each writing one value to session state. Cheap classifiers run on flash-lite; only the steps where judgement matters spend a slot on the slower model, because that slower model is capped at 5 requests per minute.

issue_triage/prompts.py

Toolsboundary

Four narrow operations against GitHub, plus one that reads the target repo’s own architecture doc to ground the module classification. fetch_issue deliberately strips labels — those are the answer key. The docstrings are the model’s API contract.

issue_triage/tools/

Guardsrefuse & suspend

Two separate concerns. Validation rejects labels that don’t exist in the repository — cheap, absolute, never consults the model. Authorisation suspends the entire run until a human confirms.

A worked example

One real run, end to end

Issue 231 — a Room dependency bump that touches a database schema on users’ devices. 22 seconds, 30 events, seven agents.

Each agent’s entire output is one word. That is why the dev UI looks sparse: there is no prose to read, just seven short answers accumulating into a dictionary. The result is the session state, not the chat transcript. 

$ ./scripts/demo.sh 10

  field       predicted          human label
  kind        enhancement        —                  ·
  area        area/android       area/android       ✓
  priority    priority/p3        priority/p2        ✗
  readiness   ready-for-human    ready-for-human    ✓

Two right, one wrong — and you can see which. It called the Room bump p3; the human who filed it said p2. That is a priority-prompt problem, not an area-prompt problem, and the per-field table is what tells you so.

Finding — step 5

A gate that refuses, versus a gate that suspends

The first version of the approval gate was a flag in session state checked by a callback. It demonstrated beautifully — the model asked to write, the callback said no. But session state is inside the trust boundary, and the run never actually stopped; it just got an error string back that the model was free to narrate around.

ADK ships the real primitive. require_confirmation takes a callable, invoked with the tool’s own arguments, so the policy depends on what is actually being written: 

apply_labels(231, ["area/core"])                 → executes
apply_labels(231, ["area/core", "priority/p0"])  → SUSPENDS

Filing an issue under a module is reversible. Asserting p0 is a claim about someone’s week. 

[triage_coordinator] → tool apply_labels({'labels': ['area/android', 'priority/p2'], 'number': 231})
[triage_coordinator] → tool adk_request_confirmation({'originalFunctionCall': {...}})
[triage_coordinator] ← tool apply_labels: {'error': 'This tool call requires confirmation'}

  *** RUN SUSPENDED — confirmation required ***
      call_id=call_286050

Why this is the part worth understanding

On suspend, ADK emits a confirmation request carrying the original function call intact, and the invocation stops. The model is not running. So no sentence in the conversation can approve it — approval has to arrive as a structured ToolConfirmation from whoever drives the runtime. That is the difference between a gate that returns an error and a gate that halts a machine.

Finding — step 8

The experiment failed, and that is the result

The plan was an ablation: remove the repository module map from the area prompt, change nothing else, and see what it costs.

FieldGroundedAblatedDeltaPrompt changed?
area91.7%83.3%−8.4ppyes
kind50.0%80.0%+30.0ppno
priority50.0%41.7%−8.3ppno
readiness66.7%66.7%0no
overall64.9%67.6%+2.7pp—

The tidy story would be “removing the grounding cost 8 points.” It isn’t supportable. kind moved thirty points on a prompt that is byte-for-byte identical between the two runs. Run-to-run variance at 12 cases is larger than the effect being measured, so the 8-point area delta is one issue changing its mind.

It only surfaced because the scorer grades every field separately. Three unchanged prompts sitting in the same table were an accidental control channel. The aggregate — 64.9% to 67.6% — would have looked like mild noise and said nothing, and a single similarity score would have hidden it completely.

The mistake worth not repeating

I designed the ablation, got a delta in the direction I expected, and nearly wrote it down as a result. The control was there by accident, not because anyone planned one. temperature is now pinned to 0, which should have been true from the first run — but that alone will not fix a sample size this small.

Two things that cost real money or real data

Guardrails to keep in mind

The API key must stay on the unbilled project

It is issued against a project with billing disabled — that is what keeps it on the free tier. A key on any project with billing enabled would auto-upgrade to a paid tier and bill per token. Free-tier prompts are also used to improve Google’s products, which is why the tool layer hard-limits the agent to public repositories in code rather than asking a prompt to be careful.

One process on the key at a time

The rate limiter keeps its window in memory; the quota is per project. An eval run died part-way through because a single triage was run alongside it — both processes believed they were under 15 requests per minute and together were not. Headroom absorbs clock skew, not this.

One more thing

Why none of these would be A2A services

Seven agents sharing one session’s state, inside one request, with one owner and one deploy. A network boundary between them would buy nothing and cost a serialisation format, a failure mode per hop, and seven things to deploy. A2A earns its complexity when an agent has a different owner, deploy cadence, scaling profile, or trust boundary — none of which is true here. Local composition until there is a deployment reason to cross.
